# Testcontainers とは

## 人間がDockerを管理するな、<br>テストコードに管理させろ

テストのライフサイクルに合わせて、<br>コンテナを**自動で起動・破棄**

`docker-compose up` すら不要

<!--
対応言語: Python(FastAPI)、Ruby(Rails)、TypeScript など。
ただしRuby版には後で触れる落とし穴あり、と予告しておく。
-->

# ① 動的ポート割り当て

ホスト側のポートを**固定しない**

Dockerに「今空いているポート」を割り当てさせ、<br>その値をテストコードに自動で返す

## 絶対にポートが衝突しない

<!--
実際に手元で試したら 32867 が割り当てられた。範囲は環境によって変わる。
-->

---

# ② ウェイト戦略

`Running` になっても、<br>中のPostgresはまだクエリを受け付けない

Testcontainersはログを監視し、

```
database system is ready to accept connections
```

を検知するまで**安全にブロック**

## `time.sleep` が不要な理由

# ③ 死神 Ryuk

```text
[ テストコード ]                      [ 死神 Ryuk ]
       |                                    |
       |===== (1) TCPソケット接続 =========>| (命綱)
       |                                    |
       |--- (2) 登録（消す対象のラベル）--->| (デスノートに記帳)
       |                                    |
    [ 💥 大爆発 / Ctrl+C ]
       |                                    |
       x - - - (3) TCP自動切断 - - - - - - -x (心停止を検知)
                                            |
                                            |-- (4) 10秒後、発動
                                            v   該当コンテナを強制削除
```

# なぜこれが美しいのか

## 死にゆく当事者に、<br>片付けを期待していない

* 掃除の責任を**別コンテナ**に外出し（サイドカー）
* **ソケット切断**をトリガーに外部が片付ける（ウォッチドッグ）

プロセスがクラッシュする限り、確実に片付く

<!--
正直に添える: Dockerデーモンが落ちたり電源が切れれば、Ryukも一緒に死ぬ。そこは限界。
-->

# Railsではどうすべきか

**モノリスなら** Rails標準のトランザクション管理 + VCR で十分そう。知らんけど

**Testcontainersが効くのは**
* 環境構築を完全に自動化したいとき
* 複数コンテナのE2Eテストをしたいとき

「後片付け」と「DBの用意」は別の仕事。併用もできる
